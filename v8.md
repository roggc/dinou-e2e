# Dinou v8: Guía de Arquitectura, Cambios y Traspaso de Conocimiento

Este documento detalla todas las novedades, motivaciones arquitectónicas, cambios disruptivos (*breaking changes*) y correcciones de errores introducidas en **Dinou v8.0.0** con respecto a la versión **v7.3.0**. Está diseñado específicamente para servir como base de conocimiento para la documentación oficial (`dinou-docs`), guías de migración y asistentes de IA.

---

## 1. Resumen Ejecutivo: ¿Qué es Dinou v8?

**Dinou v8** consolida la madurez del framework mediante dos pilares fundamentales:
1. **Migración completa a ECMAScript Modules (ESM puro)**: Eliminación de la fragmentación de extensiones (`.mjs` vs `.js`), adopción de `"type": "module"`, modernización radical del mapa de exportaciones (`exports`), y migración de las herramientas CLI y de eyección (`eject`) a ESM nativo.
2. **Estabilidad y corrección en el enrutamiento híbrido (Handler)**: Corrección crítica en la resolución de layouts estáticos con `allowISG: false`, eliminando falsos errores 404 y garantizando la entrega fluida de Server Components y Server Functions.

Dinou mantiene intacta su filosofía: **Full-Stack React 19 con RSC nativo, Server Functions, Streaming Progresivo, Dual-Bundle sin forks y Cero Vendor Lock-in** en Node.js, Bun, Deno y Cloudflare Workers.

## 2. Migración a ESM Puro (`"type": "module"`)

### 2.1. Adopción de `"type": "module"` en `package.json`
En la v7, Dinou operaba como un paquete híbrido, lo que obligaba a utilizar la extensión `.mjs` para archivos que requerían ESM explícito y `.js` para módulos que debían convivir con CommonJS.

En **Dinou v8**, el `package.json` raíz del framework declara oficialmente:
```json
{
  "name": "dinou",
  "version": "8.0.0",
  "type": "module",
  "main": "./dinou/index.js",
  "bin": {
    "dinou": "./cli.js"
  }
}
```
* **Mantenimiento pragmático de `"main"`**: Aunque Node.js prioriza `"exports"` sobre `"main"`, se mantiene `"main": "./dinou/index.js"` como estándar de la industria (siguiendo a Vite, Astro y Hono) para dar soporte a herramientas de análisis estático, extensiones de IDE y scripts de monorepos que inspeccionan directamente este campo.

---

### 2.2. Unificación de Extensiones del Código Fuente (`.mjs` ➔ `.js`)
Se ha eliminado por completo la dispersión de extensiones dentro de la carpeta del framework. Todos los scripts de compilación, adaptadores y puntos de entrada han sido renombrados de `.mjs` a `.js` estándar:

| Archivo en Dinou v7 (Obsoleto) | Archivo en Dinou v8 (Estándar ESM) | Propósito |
| :--- | :--- | :--- |
| `dinou/node/build.mjs` | `dinou/node/build.js` | Compilador de producción para Node.js |
| `dinou/cloudflare/build.mjs` | `dinou/cloudflare/build.js` | Compilador para Cloudflare Workers |
| `dinou/deno/build.mjs` | `dinou/deno/build.js` | Compilador para Deno Deploy |
| `dinou/bun/build.mjs` | `dinou/bun/build.js` | Compilador nativo para Bun |
| `dinou/esbuild/build.mjs` | `dinou/esbuild/build.js` | Compilador de cliente Esbuild |
| `dinou/core/export-static.mjs` | `dinou/core/export-static.js` | Exportador SSG estático |
| `dinou/adapters/node.mjs` | `dinou/adapters/node.js` | Adaptador HTTP servidor de Node.js |
| `dinou/index.mjs` | `dinou/index.js` | Punto de entrada unificado del framework |
| `dinou/server.mjs` | `dinou/server.js` | Utilidades de revalidación y servidor |

> [!NOTE]
> La única excepción deliberada es el artefacto compilado `.dinou/node/server.mjs`, que conserva la extensión `.mjs` para que Node y Bun siempre lo ejecuten en modo ESM independientemente de la configuración de la aplicación consumidora.

---

### 2.3. Modernización del Mapa de Exportaciones (`exports`)
Se ha eliminado la bifurcación condicional antigua (`import` vs `require`). Ahora todas las sub-rutas resuelven directamente a módulos ESM `.js`:

```json
"exports": {
  ".": {
    "types": "./dinou/index.d.ts",
    "import": "./dinou/index.js",
    "default": "./dinou/index.js"
  },
  "./env": {
    "types": "./dinou/env.d.ts"
  },
  "./server": {
    "types": "./dinou/server.d.ts",
    "import": "./dinou/server.js",
    "default": "./dinou/server.js"
  },
  "./config": {
    "types": "./dinou/index.d.ts",
    "import": "./dinou/core/config.js",
    "default": "./dinou/core/config.js"
  },
  "./adapters/node": "./dinou/adapters/node.js",
  "./adapters/bun": "./dinou/adapters/bun.js",
  "./adapters/deno": "./dinou/adapters/deno.js",
  "./adapters/cloudflare": "./dinou/adapters/cloudflare.js",
  "./adapters/netlify": "./dinou/adapters/netlify.js"
}
```

---

### 2.4. Modernización del CLI (`cli.js`) y Ejector (`eject.js`)

1. **`cli.js` en ESM Nativo**:
   - Reemplazados todos los `require(...)` por importaciones estáticas de ESM (`import { program } from "commander"`, `import { execSync } from "node:child_process"`, `fileURLToPath(import.meta.url)`).
   - Todas las invocaciones a scripts internos (`dinou dev`, `dinou build`, etc.) ahora llaman a los correspondientes scripts `.js`.

2. **`eject.js` Modular e Idiomático**:
   - Se eliminó el código suelto a nivel raíz con efectos secundarios inmediatos.
   - Ahora encapsula la lógica en una función exportada limpia:
     ```js
     export function eject() { ... }
     export default eject;
     ```
   - En `cli.js`, el comando `eject` realiza la importación dinámica y ejecución explícita:
     ```js
     const { eject } = await import("./eject.js");
     eject();
     ```
   - Se actualizaron todos los scripts generados en el `package.json` eyectado (`ejectedScripts`), reemplazando todas las rutas `.mjs` por `.js`.

---

### 2.5. Limpieza de Archivos Redundantes (`dinou/config.js`)
En versiones anteriores existía un archivo puente en la raíz de `dinou/`: `dinou/config.js`. Este archivo era un residuo de la época de CommonJS donde se requería un archivo físico en la raíz para resolver `import "dinou/config"`.

En Dinou v8:
- Se ha **eliminado definitivamente `dinou/config.js`**.
- La única fuente canónica de verdad para la configuración es `dinou/core/config.js`.
- Tanto `import { defineConfig } from "dinou/config"` como `import { defineConfig } from "dinou"` están plenamente soportados y tipados.

## 3. Singleton Universal del Edge Renderer (`globalThis.__DINOU_EDGE_RENDERER__`)

### El Problema Técnico en el Dev Server de Node
Dinou utiliza una arquitectura **Dual-Bundle** (un único proceso que ejecuta simultáneamente el motor RSC y el motor SSR). 
En versiones previas con CommonJS, Node resolvía `react-server-dom-webpack/server.edge` dinámicamente mediante `require()`. Al migrar a ESM nativo, intentar resolver e importar dinámicamente el renderer edge de React generaba discrepancias de contexto entre el código compilado por Esbuild en caliente y el servidor HTTP de Node.

### La Solución Arquitectónica
En `dinou/node/dev.js` y `dinou/node/bundle-dual-engine.js`, Dinou importa el renderer nativo de React y lo expone a través de una variable global compartida antes de arrancar los motores:

```js
import * as edgeRenderer from "react-server-dom-webpack/server.edge";
globalThis.__DINOU_EDGE_RENDERER__ = edgeRenderer;
```

Dentro del bundle del servidor interno:
```js
const edgeRenderer = globalThis.__DINOU_EDGE_RENDERER__ || await import("react-server-dom-webpack/server.edge");
```

**Beneficios:**
- **Contexto único garantizado**: Elimina duplicaciones del módulo de React Server DOM.
- **Rendimiento óptimo**: Cero latencia por re-importaciones dinámicas en cada petición HTTP.
- **Robustez en Windows y Linux**: 100% de tests verdes en todas las plataformas y bundlers (Esbuild, Rollup, Webpack).

## 4. Corrección Crítica en el Handler: Layouts con `allowISG: false`

### Contexto del Bug (v7.3.0)
En Dinou, las rutas pueden configurar generación estática e incremental mediante las funciones de layout (`layout_functions.ts / .js`):
- `revalidate = false`: Generación estática completa (SSG).
- `allowISG = false`: Indica que no se deben generar páginas dinámicas al vuelo si no fueron pre-renderizadas en el build o autorizadas explícitamente en `getStaticPaths`.

En v7.3.0, el manejador de peticiones (`dinou/core/handler.js`) contenía una condición demasiado estricta en producción:
```js
// ❌ Código con bug en v7.3.0:
if (!isDevelopment && lConfig.allowISG === false) {
  return new Response("Not Found", { status: 404 });
}
```
Esto provocaba que **cualquier petición a una ruta que descendiera de un layout con `allowISG: false` devolviera de forma fulminante un `404 Not Found`**, ignorando por completo:
1. Si los parámetros de la URL coincidían con una ruta estática autorizada mediante `getStaticPaths`.
2. Si el artefacto estático pre-renderizado (`layout.rsc`) ya existía en disco en `.dinou/dist2/`.

### La Solución Implementada (v8.0.0)
El archivo `dinou/core/handler.js` ha sido corregido para comprobar de forma exhaustiva la validez de la ruta estática antes de bloquearla:

```js
// ✅ Corrección en v8.0.0:
let isPathAllowed = false;

// 1. Comprobar si la ruta está autorizada explícitamente por getStaticPaths
if (lConfig.staticPathsSet) {
  const sortedEntries = Object.entries(lParams || {})
    .sort((a, b) => a[0].localeCompare(b[0]))
    .map(([k, v]) => {
      if (Array.isArray(v)) return [k, v.join(",")];
      return [k, String(v)];
    });
  const serializedQuery = JSON.stringify(sortedEntries);
  const singleVal = Object.values(lParams || {})[0];
  const singleValStr = Array.isArray(singleVal) ? singleVal.join(",") : String(singleVal);
  isPathAllowed = lConfig.staticPathsSet.has(serializedQuery) || lConfig.staticPathsSet.has(singleValStr);
}

// 2. Si no coincide con staticPathsSet, verificar si el artefacto pre-renderizado existe físicamente en disco
if (!isPathAllowed) {
  const cleanReq = reqPath.replace(/^\//, "").replace(/\/$/, "");
  const rscPath = path.join(process.cwd(), ".dinou/dist2", cleanReq, "layout.rsc");
  if (!existsSync(rscPath)) {
    isPathBlocked = true; // Solo se bloquea si el archivo no existe realmente
    break;
  }
}
```

**Resultado:**
- El flujo completo **SSR ➔ Loading ➔ Streaming ➔ Client Component Hydration** en layouts estáticos funciona ahora al 100%.
- Las Server Functions invocadas desde Client Components dentro de layouts estáticos se resuelven con total fiabilidad.

## 5. Guía de Migración de v7.x a v8.0.0

### Para Aplicaciones que Usan Dinou (`dependencies: { "dinou": "^8.0.0" }`)

1. **Declarar `"type": "module"` en `package.json`**:
   Las aplicaciones creadas con Dinou deben tener `"type": "module"` en su `package.json`:
   ```json
   {
     "name": "mi-app-dinou",
     "type": "module",
     "dependencies": {
       "dinou": "^8.0.0",
       "react": "^19.3.0",
       "react-dom": "^19.3.0"
     }
   }
   ```

2. **Renombrar `dinou.config.mjs` (Opcional pero Recomendado)**:
   Al usar `"type": "module"`, ya no es necesario forzar la extensión `.mjs`. Puedes usar `dinou.config.js` o `dinou.config.ts` directamente:
   ```js
   // dinou.config.js
   import { defineConfig } from "dinou/config"; // o también import { defineConfig } from "dinou";

   export default defineConfig({
     // Configuración de Dinou v8
   });
   ```

3. **Sin cambios en el código de aplicación**:
   - La sintaxis de rutas en `src/routes/` (`page.tsx`, `layout.tsx`, `page_functions.ts`, `layout_functions.ts`) **no sufre ninguna modificación**.
   - Los componentes de servidor (RSC), componentes cliente (`"use client"`), Server Functions (`"use server"`), y hooks de navegación (`useRouter`, `usePathname`, `useSearchParams`, `<DinouCacheSlot>`) son 100% compatibles.

---

### Para Proyectos Eyectados (`dinou eject`)

> [!CAUTION]
> **Peligro de sobreescritura**: La eyección (`dinou eject`) copia el código fuente del framework sobre la carpeta local `./dinou/`. Si ya habías eyectado en v7 y aplicaste cambios propios en el core, ejecutar `npx dinou@8.0.0 eject` **machacará** tus modificaciones locales.

Si ya tienes un proyecto funcionando con Dinou v7 eyectado:

1. **Tu proyecto ya es autónomo y funciona:** No es necesario que te compliques transformando manualmente tu código local eyectado a ESM puro si ya estás cómodo con tu arquitectura actual.
2. **Si necesitas el fix de `allowISG: false` en layouts:** Basta con que apliques directamente el parche en tu archivo local `./dinou/core/handler.js` (ver la Sección 4 de este documento para verificar `staticPathsSet` y la existencia de `layout.rsc` antes de bloquear con 404).
3. **Si quieres migrar al nuevo core de Dinou v8 (ESM nativo):**
   - Haz un respaldo o commit de tu carpeta local `./dinou/` con tus modificaciones previas.
   - En un entorno o rama limpia, instala la dependencia `"dinou": "^8.0.0"` y ejecuta `npx dinou eject` para obtener la estructura limpia de v8 en ESM puro.
   - Re-aplica tus personalizaciones sobre el nuevo core de v8.
